# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A real-time gamified routine/chore system for children, run as a kiosk-style PWA (typically on a Raspberry Pi 4). Kids see scheduled routines, complete tasks, earn stars, do chores and school exercises, and redeem rewards. Parents manage everything at `/parent`. UI strings are largely in Greek.

Stack: Fastify 5 + TypeScript + WebSockets + node-cron (backend), React 19 + Vite + Framer Motion (frontend), JSON files for config and SQLite (`node:sqlite`, Node 24) for runtime state, Docker Compose for everything.

## Agent rules

(`.cursorrules` repeats these four for Cursor and points here: change them here, then there.)

- Don't modify the host: no global installs or system config changes. Use Docker for any tooling or services.
- The family's data on piserve is live (see «Deployment target»). A change to the data model stays compatible with it or comes with a migration (state: a new entry in `MIGRATIONS` in store.ts; config: a step for the owner to run). Only the dev data may be recreated from mock data.
- Before committing, always check `git status` and `git diff`. Never `git add .`; add files by name. Split commits into logical chunks using `<type>(<scope>): <subject>` (types: feat, fix, docs, refactor, test, chore…; scopes: backend, frontend, shared, docker, config).
- If the data model changes, update `shared/types.ts` **and** the matching JSON schema in `backend/*.schema.json` (state: `state.schema.json` and the store.ts migration too). Otherwise validation will reject the data.

## Pull requests

One issue per PR, kept compact, written for the owner to review from the PR page alone. Follow `.github/pull_request_template.md`: **Before** (the problem shown: screenshot, video with sound, failing test, code at file:line), **Problem**, **Fix**, **After** (the same evidence, now right), **Blast radius** (what else it touched, any manual step for piserve's live data). Capture screens on the dev stack with Playwright at the kiosk size (1280×800) and any other size the change affects; `tools/evidence/` records scenarios as screenshots and videos with sound (see its README). Before closing the issue, record the decision where the next agent will look (this file or the tool's README).

Docs (#37): README.md is the human entry point (run, test, release, a map of the docs) and links here for the architecture instead of restating it; this file is the architecture doc. index.md and frontend/README.md are gone, and `.cursorrules` is only a copy of «Agent rules» for Cursor: don't grow a second architecture doc. A change that moves a command, route, file, screen or a server answer updates the doc that names it (README.md, VALIDATION.md, CUSTOM_SOUNDS.md, GITHUB_TOKEN.md, BACKUP.md, a tool's README) in the same PR; their examples are real replies from the dev stack, not written from memory.

The drill, when the owner names an issue: the `issue` workflow (`.claude/workflows/issue.js`) runs it in stages, and each stops for the owner's reactions.
1. **Scope** (`{issue, stage: "scope"}`): read the issue and #51, branch `issue-<n>-<slug>`, record the Before evidence in `.evidence/<n>/`, plan, and have a critic challenge it. Show the owner the brief, the critique and the evidence; wait.
2. **Build** (`{issue, stage: "build", notes}`, with the owner's reactions verbatim): fix, After evidence from the same scenario, checks, the mark, `.evidence/<n>/PR.md`; an adversarial review and one round of fixes. Show the owner the draft; wait. More notes, build again.
3. **Ship**, only on the owner's word, from the main session: `tools/evidence/publish.sh <n>`, push the branch, `gh pr create --body-file .evidence/<n>/PR.published.md`, and comment the blast radius on the issue.

## Commands

Everything runs in containers. The dependencies live in the container-mounted `node_modules`.

```bash

docker compose -f docker-compose.yml -f docker-compose.dev.yml up

# Prod-like build (docker-compose.override.yml is auto-loaded): nginx on ${FRONTEND_PORT:-80}
docker compose up --build

# Add a package / type-check / lint inside the running dev containers
docker compose -f docker-compose.yml -f docker-compose.dev.yml exec backend npm install <pkg>
docker compose -f docker-compose.yml -f docker-compose.dev.yml exec backend npm run build      # tsc
docker compose -f docker-compose.yml -f docker-compose.dev.yml exec frontend npm run build     # tsc -b && vite build
docker compose -f docker-compose.yml -f docker-compose.dev.yml exec frontend npm run lint      # check-help, check-voice, check-sound, check-gender, then eslint (0 problems, warnings fail too)

# The owl's voice: record every help bubble that is new or changed, audit, list what to commit (dev machine: NVIDIA GPU, Docker)
tools/help-voice/run.sh
# The screens' sounds, rarely: fetch the CC0 packs, then choose and make the palette (see tools/sfx/README.md)
tools/sfx/fetch.sh

# data.json against its schema, then a legacy state.json (an ENOENT line when there is none); prints, exits 0 either way
docker compose -f docker-compose.yml -f docker-compose.dev.yml exec backend npm run test-schemas

# Backend tests (node:test, every backend/test/*.test.ts)
docker compose -f docker-compose.yml -f docker-compose.dev.yml exec backend npm test
# Frontend tests (node:test on src/**/*.test.ts, types stripped by Node)
docker compose -f docker-compose.yml -f docker-compose.dev.yml exec frontend npm test

# Import state.json + logs.jsonl into the database (if not done yet) and verify record by record (prod image)
docker compose exec backend npm run migrate

# Take a backup now, into BACKUP_DIR (prod image; dev stack: npm run backup:dev). Restore one: ./restore-backup.sh <folder>
docker compose exec backend npm run backup
```

Beyond `npm test`, verify changes manually:
- `/?push=<id>`, `POST /api/hooks/push` and the parents' «Ξεκίνα τώρα» start exactly that flow, routine assignment or `alarm`, now (`triggerAction(id, 'push_hook')`), never the other schedules due at the same time (#29). A push of a kid's routine while she is already in one keeps hers: the answer is `{ skipped, runningId }` and the parent's toast says «Ήδη σε ρουτίνα».
- `POST /api/debug/time` (`{"time": "07:00"}` today in `settings.timezone`, or an ISO date) simulates that minute: every schedule due then starts, logged as `SCHEDULE_MATCH`. `GET /api/debug/schedule` lists each schedule's next run.
- `GET /api/debug/logs` returns recent action logs.

### CI

`.github/workflows/ci.yml` («Checks», #40) runs on every PR, every push to master and first thing in the image build, three jobs in parallel on Node 24 (the images' major): **backend** (`npm run build`, `npm test`, `npm run test-schemas`, which reports only until #53 makes it exit 1), **frontend** (`npm test`, `npm run lint`, `npm run build`, which ends with `scripts/check-bundle.mjs`) and **problem-gen** (its tsc and tests, then all four generators rerun and `git diff --exit-code backend/exercise-pools`, then `audit.ts`). A fourth job, on PRs and pushes only, runs `docker build` of both Dockerfiles for linux/amd64 without pushing, so a Dockerfile-only break shows before `build.sh`. CI has no GPU: it checks the committed clips, sounds and pools and never makes them, so record (`tools/help-voice/run.sh`) and regenerate (`tools/problem-gen`) before pushing. The regenerate-diff is why a hand edit of a `*-generated.json`, or a family changed without rerunning its generator, turns a PR red. It also depends on Node's ICU/CLDR data (numbers go through `toLocaleString('el-GR')`): if a Node update changes that formatting, master goes red too; regenerate the pools and commit them in their own PR. A red check is fixed, not overridden. To add a check, add a step to ci.yml; the image build gets it through `workflow_call`. To try the jobs locally, nektos/act runs ci.yml as is (in Docker, image `catthehacker/ubuntu:act-latest`), each job from a clean clone; the docker job's gha cache only works on GitHub.

## Deployment target

We develop here, but production runs on **piserve**: `ssh piserve`, checkout at `~/work/girls_gamiefied_routine`, deployed with `deploy-rpi.sh`. The Pi's `backend/data.json`, `backend/routine.db` (and, until migrated, `backend/state.json` + `backend/logs.jsonl`) hold the **live family data** (star balances, history). They have uncommitted local changes there, so never overwrite them with the dev copies, and never `git checkout`/`reset` them on the Pi. Any config or schema change must stay compatible with that existing data, or come with a migration step.

Backups (BACKUP.md): the backend backs up the database, data.json, exercises.json and uploads/ every day at `BACKUP_CRON` (03:17, process TZ), and at startup when the newest backup is over a day old, into the host folder named by `BACKUP_DIR` in `.env` (mounted at /backups; default `./backups/daily`, on the SD card, with a "same filesystem" warning in the log and the action log until it points at a USB disk or NAS), keeping `BACKUP_KEEP` (14). `restore-backup.sh <folder>` puts one back: checksums first, the live files set aside in `backups/pre-restore-<stamp>/`, never deleted. Setting the destination on piserve is the owner's step (fstab with nofail, BACKUP_DIR in .env, redeploy).

Release: `./build.sh` / `build.ps1` triggers the GitHub Actions workflow (`.github/workflows/docker-build.yml`, manual dispatch only: a push to master builds nothing). Its first job runs the Checks (ci.yml); if one fails, nothing is built or pushed and the tags stay where they were. It builds multi-arch images to `ghcr.io/nkyriazis/routine-{backend,frontend}`, tagged `:latest` and `:sha-<first 7 of the commit>`; to roll back, point `docker-compose.release.yml`'s `image:` at an older `sha-` tag. On the Pi, `deploy-rpi.sh` pulls them using `docker-compose.release.yml`. Don't use dev mode on the Pi, because the polling file watchers use too much CPU. The images bundle what is committed and generate nothing. Compose and CI build both images with the repo root as context, so the root `.dockerignore` is the only one Docker reads (one in `frontend/` or `backend/` does nothing): whatever a tool leaves in the tree, local or generated, gets a line there (#38). The owl's voice clips (`frontend/public/help-voice/`, `src/help/voice/clips.json`) and the sounds (`frontend/public/sfx/`, `src/sound/sounds.json`) are made on the dev machine and ship as plain files in the frontend image, precached by the PWA. So after changing a help bubble, run `tools/help-voice/run.sh` and commit its output before building. `npm run check-voice` fails while a bubble has no clip.

## Architecture

### Persistence: config vs. state
- **Config** (`config.ts`) lives in `data.json` (`DATA_FILE`) and `exercises.json` (`EXERCISES_FILE`), validated with AJV against `data.schema.json` / `exercises.schema.json` (`schemas.ts`). It is cached in memory (deep-frozen) and re-read only at startup, after an admin edit (`writeRawConfig`) and when the file changes on disk (stat polling). An invalid file never replaces the cache: the last valid config stays live (or, when the file was unreadable since the start, an empty fallback) and the error goes to clients as `configError` (with `file` and `emptyFallback`) in the state and to `/api/admin/validation-status`. Use `config()` to read it, `readRawConfig()` for a mutable copy. A oneOf whose branches are told apart by `type` (exercise items, flow steps, parallel actions) carries `discriminator: { propertyName: 'type' }` and `type: object` (the Ajv instances in schemas.ts and test-schemas.js enable `discriminator`), so a mistake is one error in the branch its tag names, not one per branch. Give a new tagged oneOf the same.
- **Checks the schema can't express** are a `ConfigFile`'s `rules`; data.json's live in `backend/src/configChecks.ts` (`configProblems`), and a new check goes there, with its case in `test/configChecks.test.ts`. They are: `schedules[].cron` and `chores[].availabilityCron` that `cron.ts` can't read (`unreadableCrons`, #89); duplicate ids per list, plus a flow with an assignment's id (one namespace); links to nothing (assignments → kids and routines, routine tasks → routines and tasks, schedules → an assignment, flow or `alarm`, parallel actions → assignments and flows, `chores[].eligibleUsers` → kids); blank kids' names and titles; flow cycles (`flowCycles`, #121: flows that start each other before an alarm, one warning per cycle at the action that closes it, naming the path; a flow that starts itself again after an alarm is none. A routine on the way still warns, since it may be skipped (busy, done today) or hold the flow, and the message says both: skipped, the closing action starts nothing; started, the cycle starts over when it closes, so a routine left with ✕ comes back every time) and an assignment or flow whose id is `alarm` (`reservedIds`, #121); colours that are neither a theme token (`shared/themeColours.ts`, the theme's `--color-*` list, which `frontend/src/styles/themeColours.test.ts` checks against variables.css; the parents' colour picker takes its values from it), a hex, a CSS colour function nor a named colour (#104). **Only a cron refuses a save** (`refuses`): one a save adds or changes is refused like a schema error, keyed by item and cron, never by array index, so one already live, left as it is, blocks nothing, and fixing it is a save. Every other kind is a **warning only** (#104 scoped refusing out): the save goes through, `/api/admin/validate` answers it in `warnings` and the Advanced JSON editor lists it in amber under the editor. A file on disk with any of them still **loads**: never a `configError` (that would keep the previous config live and turn the forms off, and piserve's live file must keep loading), but `AppState.configWarnings` (`ConfigWarning` = `CronWarning | CheckWarning`, each with a Greek `message`; also in `/api/admin/validation-status`), listed one by one in the amber banner on every parents' view (crons with «Άνοιγμα Ρυθμίσεων» and a ⚠ on the item's row, the rest by message and JSON path with «Άνοιγμα JSON»). The forms' raw cron field asks `POST /api/admin/validate-cron`.
- **Saving never writes over a config file the server couldn't load** (#45). `ConfigFile.save()` refuses while the file on disk is invalid, so no read-modify-write writer (the forms) puts the live copy over the file being fixed. The one override is `replace` (`POST /api/admin/data|exercises?replace=1`), sent only by the Advanced JSON editor: it keeps the invalid file beside as `<file>.invalid-<stamp>`, and never writes the empty fallback over a file that was never loaded. In that case the editor loads the file's own text (`GET /api/admin/{data,exercises}/text`) to fix and save. Don't add `replace` to any other writer. Nor does `save()` ever write the empty config over a live config that has content, with or without `replace`: that is what a screen holds before its first `STATE` (`EMPTY_STATE` in GameProvider.tsx). Screens that save the whole config wait for `useGame().hasState` (the Advanced config editor mounts only then; `useConfigSave` refuses before it).
- **A config save names the version it edited** (#33). `ConfigFile.version()` is the first 12 hex characters of the sha256 of the live file's text, so it moves on every save and every valid reload from disk (a hand edit on the Pi too). `AppState.configVersion` carries both files' versions (`appState()` reads `config` and its version in one `current()` call, before any await, so a STATE never pairs them wrong); `GET /api/admin/{data,exercises}` send theirs in `X-Config-Version`. Every in-app writer sends the version it edited as `?version=` and its screen as `?source=` (`form`, `advanced`, `advanced-fix`; none is logged as `api`): the forms the version of the STATE they spread, a form sheet the one it opened with, the Advanced editors the one they opened with (config: the same STATE as its text; exercises: its GET). A newer live version makes the save a 409 `{ error, conflict: true }` that writes nothing, which the screen resolves by reloading (a sheet reloads itself, an editor shows a «Φόρτωσε ξανά» banner as soon as the live version moves past its own). A 200 answers `{ success, version }`, and the editor that saved holds that version, so its own save never marks it stale. That answer (and the exercises editor's GET) arrives before the STATE carrying the same version, which `sync.changed()` builds after the reply has gone out, so until that STATE lands the editor also accepts the live version it was newer than (`behind` in JsonEditor.tsx): no banner, not even for a frame. A save without a version is not checked (scripts, curl, the editor fixing a file that doesn't parse). Every save is logged as `CONFIG_SAVED { file, source, route, changed }` (`changed`: the top-level keys that differ, `changedKeys()` in config.ts), every refused one as `CONFIG_SAVE_STALE { file, source, route, version, current }`. A new config writer must send its version and source. The state editor and hand edits on disk: next bullet (#98).
- **A state save names the version it edited too** (#98). The state's version is the first 12 hex characters of the sha256 of the snapshot's JSON (`stateText()` in db.ts, `versionOf` in config.ts), computed only when the editor opens or saves, never per STATE: `GET /api/admin/state` sends it in `X-State-Version` (the hash of exactly the text it returns), and `POST /api/admin/state?version=&source=advanced` hashes the live snapshot again in the same transaction as the replace. A different one is a 409 `{ error, conflict: true }` that writes nothing («Η κατάσταση άλλαξε στο μεταξύ (από άλλη οθόνη ή από τα παιδιά)…»), logged as `STATE_REPLACE_STALE { source, version, current }`. AppState carries no state version (hashing the whole history on every STATE would grow with the years), so the editor has no `live`: JsonEditor's 409 path lists the reason under it and shows the «Φόρτωσε ξανά» banner. Strict on purpose, no per-field compare: any change to the snapshot's tables since the editor opened (a chore confirmed, a task done, a purchase) refuses the save, so while the kids are busy it is often refused; the editor is a last resort. The idle state doesn't move (measured on the dev stack: the hash held for 4 minutes). Flows and routines on screen, tours played and the log are not in the snapshot, so they don't move it. The snapshot reads every table `ORDER BY rowid` and an update keeps a record's rowid, so an untouched state always hashes the same (`test/stateSave.test.ts`); a new table in the snapshot must keep that. A save without a version is not checked (scripts, curl). Every save is logged as `STATE_REPLACED { source ('advanced' from the editor, else 'api'), stars: { <kid>: [before, after] } (each balance it moved; a kid missing on one side counts 0), changed (the snapshot's collections that differ), cleared: { flowRuns, routineRuns } (what was on screen and was ended) }`. Hand edits on disk are logged by the watcher (`reloadConfig().files`, `logConfigReload` in db.ts): `CONFIG_RELOADED { file, changed }` for each file it reloaded, `{ file, changed: [], restored: true }` when a broken edit went back to the live text, and `CONFIG_INVALID { file, message }` once per bad text (the 2 s poll would repeat it). The server's own saves (`CONFIG_SAVED`; the reload after one finds the text it wrote) and the reload at startup log nothing.
- **Daily backup** (`backup.ts`, run in a child process by `backupSchedule.ts` so a slow disk can't block the event loop): `VACUUM INTO` (one consistent file, `integrity_check`ed), data.json and exercises.json byte for byte, uploads/, and `SHA256SUMS`, written as `.partial-<stamp>` and renamed when complete; rotation only deletes folders it named. A run still going after `BACKUP_TIMEOUT` (7200 s) is killed and logged as `BACKUP_FAILED` with `reason: 'timed out'`, so a hung disk never stops the next runs. Results go to the action log as `BACKUP`/`BACKUP_FAILED`. `POST /api/debug/backup` runs the server's own path.
- **Runtime state and history** (`store.ts`) live in SQLite at `DB_FILE` (default: `routine.db` next to `data.json`, i.e. on the `/data` volume): user stars, routine/task executions, spendings, transfers, chore instances, exercise sessions/assignments and the action log. Every change is written through immediately (WAL, `synchronous=FULL`); there is no in-memory copy. Multi-step changes use `store.transaction()`. Schema changes are appended to `MIGRATIONS` in store.ts. If the data model changes, update `shared/types.ts`, the table columns in store.ts (new migration) and `state.schema.json`.
- **Legacy files** (`migrate.ts`): on first start the backend imports `state.json` (`STATE_FILE`) and `logs.jsonl` (`LOGS_FILE`) once, in one transaction, and records it in the `meta` table. It never writes those files. `npm run migrate` runs the same import and prints a record-by-record verification.
- `/api/admin/state` reads and replaces the whole state as a `StateSnapshot` (the old state.json shape, validated by `state.schema.json`), with its version (`X-State-Version`, `?version=`, #98 above).
- **Action log**: `logAction()` inserts into the `action_logs` table; `/api/debug/logs` returns the newest entries.
- The backend is the source of truth. Mutations go through db.ts helpers such as `awardStars`, `claimChore`/`attemptChore`/`confirmChore`/`rejectChore` and `triggerAction`.
- **Stars invariant**: a kid's available stars (`getAvailableBalance`, `User.available`) are her balance minus the stars promised in her pending outgoing gifts, and no balance goes below zero. Every star change goes through db.ts, in one transaction: `buyReward`, `takeStars` (a parent's take-away) and `createGift` check the available stars, `resolveGift` re-checks the sender's balance on approve, and `awardStars` only adds. A refusal is a `StarsError`, sent as a 400 with a Greek reason the parent's toast shows. Only the whole-state writers (`replaceState`, the legacy import) set balances directly. A repeated `POST /api/spendings` counts as a second purchase (no idempotency key): it is bounded by the available stars and the parent revokes a duplicate, which refunds it.

### Real-time flow (backend/src/sync.ts)
- Clients render one `AppState` (`shared/types.ts`) and nothing else. Every store write (the `Store` change hook) and every config change calls `sync.changed()`; the server then rebuilds `appState()` (db.ts) and sends it as a `STATE` message to every client over WebSocket `/ws`. Changes in one event-loop turn are sent once, builds never overlap, and a connecting client gets the state the same way, so reconnects and restarts need nothing special. Mutations don't have to remember to notify anyone.
- STATE carries the current world, never the archive (#34): every purchase and gift still pending whatever its age, those decided in the last `HISTORY_DAYS` (30, `shared/types.ts`; by `resolvedAt`, else `createdAt`), and each kid's last `LAST_REWARDS_GIVEN` (10) rewards given whatever their age, which her store lists. Records name kids and rewards by id; clients look them up in `users`/`config.rewards`. Ιστορικό reads everything decided (purchases, gifts, the closed chores the database keeps for 7 days, and every finished exercise, #68) over REST, `GET /api/history` (db.ts `history()`), a page of 30 from a cursor, optionally for one kid; it reads the first page again on each STATE and keeps its pages to itself, never in GameContext. `/api/admin/state` stays the complete snapshot. `backend/test/stateSize.test.ts` holds a budget for STATE's history part only (users, rewards, purchases, gifts: under 16 KB after three busy years). The other lists bound themselves: `choreInstances` (open, plus closed in the last 24h), `exerciseAssignments` (today's), `exerciseSessions` (running, plus finished in the last 30 min and not closed), `flowRuns`/`routineRuns` (on screen), `helpSeen` (tours × kids), `config`. Anything added to AppState must be bounded by time or count like these, never by how long the family has used the app. Building STATE still reads the two tables whole (no index on the time), which is fine at a family's rate. `/ws` deflates its messages (permessage-deflate; Vite's proxy and nginx pass it through): a STATE travels at about a quarter of its size.
- `GameProvider.tsx` (context/) replaces its state with each `STATE`; screens read it with `useGame()` (context/GameContext.ts). There is no initial REST fetch and no per-event patching. To show something new, add it to `AppState`/`appState()`.
- Flows and routines on screen are server state too (`flowRuns`, `routineRuns`; tables `flow_runs`, `routine_runs`). The server starts and advances them (db.ts, "ROUTINES AND FLOWS ON SCREEN"); the kids' dashboard only renders them and reports actions: dismiss an alarm, complete a task, close a routine. Those REST calls name the step/task they act on, so repeats from a second device are no-ops. A reload or a server restart resumes where it was. An alarm nobody dismisses stops after `settings.alarmMinutes` (default 60), with the rest of its flow (`expireAlarms`, every minute and at startup), so a screen opened later doesn't ring a morning alarm. An alarm already running when the page loads sits under the start overlay («Πάτα για να ξεκινήσουμε!») and can't sound until that tap (browsers' autoplay rule), so `useAppSounds` retries on the first touch.
- A flow never starts a flow whose own start is still under way (#121): `startFlow` keeps that stack (`startingFlows`), and a flow action naming one of them logs `FLOW_CYCLE` and starts nothing, while the step's other actions run, so A → A and A → B → A end instead of overflowing the stack. Only synchronous recursion is refused: a flow started again after an alarm or a routine (A: alarm, then A) restarts, as from a schedule. `alarm` in a schedule, a push or «Ξεκίνα τώρα» always means the plain alarm, checked before assignments and flows; an item with that id starts only as a flow step, and the parents' page never offers it (`targetsOf`). `triggerAction` answers `nothingStarted` (and `cycle`) for a flow that ended at once, and «Ξεκίνα τώρα»'s toast says so.
- An alarm is never hidden (#25). The server says whom it is for: `FlowRun.userIds`, the kids of the routines the steps after it start, through sub-flows, up to the next alarm (empty: everyone); computed in `flowRunsView()`, not stored. On the kids' screen a kid's alarm takes her routine's slot until dismissed (her routine stays on the server and comes back as it was); an alarm for two kids is one card naming both. Dismissing it while she is in her routine skips her routine step (`startRoutine` keeps a kid's running routine), and the flow doesn't wait for the routine she started by hand: a step after it runs at once. The morning flows (dev `morning-flow`, piserve's `morning-school-flow` in `backend/data2.json`) end each kid's sub-flow at her routine, so nothing follows it today. A flow's routine step also skips a kid who already finished that routine today (#58): a flow's routine step skips a kid with an execution of the routine that started today in `settings.timezone` and finished (`completedAt`; a start left with ✕ doesn't count), logged as `FLOW_ROUTINE_SKIPPED` (`reason: 'done-today'`). Her alarm still rings and names her (the alarm isn't changed); dismissing it starts nothing for her and the flow moves on. Only flows skip: a routine started by itself (push, its own schedule, «Ξεκίνα τώρα» on the routine) starts again, while «Ξεκίνα τώρα» on a flow follows the flow rule. A routine meant to run twice a day through flows would be skipped the second time; no flow does that today. `backend/test/runs.test.ts` holds both rules. The Dashboard plays one alarm sound for all alarm cards, keyed by a string (`hooks/useAlarmSound.ts`), because every STATE replaces the props objects and an effect on them would restart the sound.
- The only events are the chore toasts (`CHORE_CONFIRMED/REJECTED/EXPIRED`) and `ROUTINE_ENDED_BY_PARENT` (#63), via `sync.notify()` and `useGame().subscribe()`. They never carry state that isn't also in `AppState`. A kids' screen still on an older bundle takes every event it doesn't know for a chore toast and shows an empty one for 5 s (recorded in #63's PR), so after deploying a new event to piserve, reload the kiosks: the Pi serves plain http, with no service worker to bring them the new bundle.
- Heartbeat: the server sends `HEARTBEAT` every 10 s; a client that hears nothing for 25 s drops the socket and reconnects.
- All messages are `ServerMessage` (`{ type, payload }`), sent to every client with no per-user filtering.

### Scheduling (backend/src/server.ts, cron.ts)
- `node-cron` runs `checkSchedules()` every minute. It matches `schedules[].cron` for the tick's minute, then calls `triggerAction(targetId)`. It also generates, expires and cleans up chore instances according to each chore's own cron (always on the real clock: `/api/debug/time` simulates schedules, not chores; it is the only thing that does, a push starts its target alone).
- Schedules and chores both match with `cronMatchesAt(expr, date, timezone)` in `backend/src/cron.ts`: cron-parser's `includesDate` on the minute, in `settings.timezone` (default Europe/Athens). It is the only place the backend decides from a cron when something happens (`nextCronRun` there serves `/api/debug/schedule` only). Full cron rules, so whatever the parent form writes is read: lists of ranges and steps (`1-3,5`, `0-30/10`), a step counts from the start of its field (`*/2` on day of month is the odd days), 0 and 7 are Sunday, day of month OR day of week. DST: a time in the skipped hour (last Sunday of March, 03:xx) never happens; one in the repeated hour (last Sunday of October, 03:xx) fires twice, which is left as is. Missed minutes stay missed (#51). A cron cron-parser can't read (`cronError`; a save refuses one, a file on disk may still have one, see Persistence) logs `SCHEDULE_CRON_ERROR` once per schedule and cron, or `CHORE_CRON_ERROR` once per chore and cron (`cronDue` in db.ts); `SCHEDULE_ERROR` is a schedule that matched and failed to start, logged every time. Other cron readers, none of which decide when a schedule or chore fires: node-cron's `BACKUP_CRON` (container `TZ`, BACKUP.md), `simpleCronToTime` in db.ts (a plain `M H` for the routine's display time) and the parent form's `frontend/src/components/parent/cron.ts` (reads and writes the `M H * * DAYS` shape).
- Flows are multi-step sequences, including alarm steps and parallel routine starts. Routines are assigned to users through `routineAssignments`.

### Backend layout
- `server.ts` holds all REST routes: `/api/*`, the `/api/admin/*` raw config/state editors plus validate and schema endpoints, uploads to `uploads/` served at `/uploads`, and the WebSocket. It exports `server` and starts only as the entry point, so a test can `require` it against its own DATA_FILE/DB_FILE and call the routes with `server.inject` (`test/bodies.test.ts`).
- Uploads (#107): one limit, `UPLOAD_MAX_BYTES` in `shared/uploads.ts` (10 MB, sized for an alarm song), for every upload (Αρχεία and every form's «Εικόνα»). The backend gives @fastify/multipart that `fileSize`; a file over it arrives cut (`file.truncated`), so `/api/admin/upload` deletes it and answers 413 `{ error: uploadTooBig(name) }` (`test/uploads.test.ts`, with its own `UPLOADS_DIR`). `frontend/nginx.conf` sets `client_max_body_size 11m` (the file plus the multipart headers) only in `location = /api/admin/upload`; every other request keeps nginx's 1m. Every other failure of the route is Greek too, naming the file: 400 `uploadNoFile`, 500 `uploadBroke(name)` (a body cut mid-file, a failed write), and the 500 path deletes what it wrote. `api.ts` refuses a bigger file before sending it, and `uploadFailed` words every failure from the status and the file name alone (413, 500, any other status, no answer), never showing the backend's raw text; Αρχεία shows the limit under the button. Αρχεία has no delete: BACKUP.md says how to delete an upload on the Pi. Change the number in shared/uploads.ts and nginx.conf together: `src/uploadLimit.test.ts` (frontend `npm test`) fails when nginx's is not above it, or is set anywhere else. There is no separate cap for images, so an avatar or icon may be up to 10 MB too. CUSTOM_SOUNDS.md tells parents the limit.
- Request bodies (#32): no route takes `request.body` on faith. Every route that reads a body declares its JSON schema from `bodies.ts` (`{ schema: { body } }`, with the matching type as the route's `Body`). Types are strict (ajv `coerceTypes: false`: "5" is not 5, true is not 1), unknown fields are ignored, and a bad or missing body is a 400 `{ error: 'body/amount must be integer' }` (server.ts's error handler) before the handler runs, so it changes nothing. The schema checks shape; meaning stays in db.ts, the one place for it: the stars rules (#24, and `confirmChore`'s whole number ≥ 0), the group game's size (`GAME_LIMITS`, which the schema imports rather than repeating, and the setup screen's own 5 × 10), known players and claimers. A new route that reads a body gets a schema in bodies.ts and a case in `test/bodies.test.ts`. The admin editors check against data/state/exercises.schema.json themselves, and the upload is multipart.
- No MCP (decided by the owner, #44, 2026-10): the MCP server, its `/mcp` route, the SDK and the ngrok tunnel profile were retired. Agents and scripts use the REST routes (`/api/*`, `/api/admin/*`) on the trusted LAN, or edit the repo. Don't bring back a `/mcp` endpoint, an MCP SDK or a public tunnel without the owner.

A file's `grades` are the grades it is written for; its optional `revision` grades get it only for a category their own grade has nothing in (b-dimotikou is Β΄ with revision Γ΄, d-dimotikou Δ΄ with revision Ε΄; since #49 part 2 Γ΄ and Ε΄ have maths of their own, `g-`/`e-dimotikou-maths.json`, since part 3a Γ΄ has language of its own, `g-dimotikou-language.json`, and since part 3b Ε΄ too, `e-dimotikou-language.json`, so b-dimotikou and d-dimotikou serve no kid in any category; keep both as the fallback). ### Frontend layout

The form adds a kid (a fresh id, 0 stars, no routines) but never deletes one: her balance, history and assignments are keyed by her id, so removing a kid stays in Προχωρημένα. A kid's colour is one of the theme's, saved as `var(--color-primary|secondary|accent|success|warning)` for contrast on the dark kids' screen; a colour written by hand in the JSON shows as «Άλλο» and is kept unless changed. Ρυθμίσεις → Ρουτίνες (`settings/RoutinesEditor.tsx`, #36) edits a routine's name, icon, colour, its tasks in order with their minutes and which kids have it; Εργασίες (`settings/TasksEditor.tsx`) edits a task's name, icon, stars and late stars. Δουλειές' Ποια παιδιά (`KidsField`) has «Για όλα» (no list) and the kids; a tap keeps only ids that are kids (`toggleKid`), so a missing kid (u3) goes on the first tap, and a line says which while one is there (#121); untouched, the value stays. A routine lives in three lists (`routines`, `routineTasks`, `routineAssignments`): the pure functions in `settings/routines.ts` (tested in `routines.test.ts`) build its draft and write it back, changing only that routine's entries and leaving every row nobody touched as it was, and one POST saves the three under one #33 version (`useConfigPatch` in `useConfigSave.ts`). A task's time lives on the routine's row (`durationSeconds`), per routine, not on the task; the form shows it in minutes rounded to a tenth and saves typed minutes as whole seconds. Ids are made by the forms, never typed: rows and new routines get `newId()` (unique within a call), a newly ticked kid's assignment `${userId}-${routineId}` (suffixed if any assignment, flow, schedule target or 'alarm' has it); an existing assignment keeps its id, because schedules and flows name it. The forms refuse, saying why: deleting a task a routine uses (naming the routines); unticking a kid, or deleting the routine, while a schedule or flow starts her assignment or she is in it on screen; and adding, removing or moving tasks of a routine on screen (a run counts its tasks by position, `taskIndex`), while its name, colour, minutes and other kids still save. A task twice in a routine, a `taskId` that doesn't exist (the JSON editor accepts both, #104) or late stars over on-time stars are shown as warnings and don't block saving the rest. Flows stay in the JSON, with no form. Each Προχωρημένα JSON editor (`advanced/JsonEditor.tsx`) gives Monaco every schema it needs at `internal://schemas/<file>`, because Monaco resolves a schema's relative `$ref` against that URI (exercises.schema.json needs data.schema.json; at `internal://data.schema.json` it would not resolve), and checks with the server before saving (`/api/admin/validate`, `validate-state`, `validate-exercises`), listing the errors under the editor in AJV's English. The config and exercises editors keep the version they opened with and show a reload banner when the live one moves past it (see the #33 bullet under Persistence); the state editor keeps its version too and shows the banner when its save is refused (#98). A refused save's 400 says what is wrong in one line (`summarize()` in schemas.ts: `<path> <message>` for the first three errors, then `(+N more)`), never AJV's JSON. A parent's toast never cuts its text: it shows up to six lines and scrolls the rest, takes touches (a tap closes it) and lives 60 ms a character, 3 to 12 s (`feedback.tsx`, `parent.css`).

- Plain http (#108): the Pi serves `http://<pi>/`, which is not a secure context, so the browser APIs that need one are undefined there (`navigator.clipboard`, service workers and more: MDN marks each «Secure context»). Copying goes through `components/parent/copyText.ts` (`copyText(text)`, tested in `copyText.test.ts`): `writeText` when it exists, otherwise a hidden readonly textarea and `execCommand('copy')`. Both start synchronously in the tap, because WebKit (Safari, and every browser on an iPhone) honours a copy only during the gesture; when `writeText` refuses it resolves false rather than try `execCommand` after the await. Its caller says what happened, and on failure shows the text to read (Αρχεία: «Δεν αντιγράφηκε. Το όνομα: …»). A new use of a secure-context API needs a fallback like this and is checked over a non-localhost address of the dev machine (here `http://192.168.122.1:5173`, the libvirt bridge; any address that isn't localhost will do), never only on localhost, which counts as secure: `tools/evidence` plays it there, in WebKit as an iPhone too (`start(out, { browser: 'webkit', device: 'iPhone 13' })`).
- Help (`src/help/`): an owl button plays a driver.js (MIT) tour of whatever screen is on top, on the kids' screens (`<HelpProvider>`, dressed in `help.css`). Widgets carry a named anchor (`{...help('store.balance')}`; names typed in `anchors.ts`); a screen wraps its content in `<HelpScreen tour={…} inline?>` and the most deeply nested open screen wins. Tours live next to their screen (`StoreModal.help.ts`), steps name anchors (missing widgets are skipped) and have stable keys (anchor or id). A problem's tour follows the step on screen and her rung; intros play once per kid. Played tours are server state (`help_seen` table, `AppState.helpSeen`, `POST /api/help/seen` and `/api/help/reset`); ids ending in `@<userId>` are a kid's own. `npm run check-help` (first thing in `npm run lint`) fails when an anchor isn't placed or explained, or a new overlay screen has no `<HelpScreen>`. When you add a widget or a screen, give it an anchor and a tour step. The owl says every bubble aloud: clips recorded at development time by `tools/help-voice/` (VoxCPM2 speaks, Whisper audits every take; see its README) ship in `public/help-voice/`, keyed by the spoken text (`src/help/speech.ts`, `voice/clips.json`; a step's `say` replaces symbols). A new or edited bubble is silent until `tools/help-voice/run.sh` records it (one command on the dev machine: records, audits, says what to commit); `npm run check-voice` (in lint) tells. The kids' screens speak the same way to every child: no «έτοιμη», «σε ποια» (use a verb, or the neuter «παιδί/παιδιά»); `npm run check-gender` (in lint) fails on gendered words in their text and speech. A new tour variant goes in `src/help/allTours.ts`. A bubble whose text depends on the kid's rung (forgiveness) lives in an intro whose id names the rung (`problem-forgiving`, `exercise-unforgiving`), so changing the text or the kid's rung makes the owl offer it again; list both rungs in allTours.ts. A bubble for a widget that is on screen only in some state (the «Δείξε μου» buttons, after wrong tries) goes in a tour variant used only in that state, with its own id (`problem-show`, `exercise-show`, one for every kind of step or exercise; an extra problem's card, #67: `exercises-extra`, `store-extra`, joined with revision by `editionId`, every combination in allTours.ts): the owl wiggles the first time the widget appears and says the bubble where it can point at it. A widget a step tells her to use carries its anchor only while she can use it: «Κι άλλο πρόβλημα», disabled at the day's limit or with 3 extras waiting, has none then, so the owl skips its step (in the drawer it points at another kid's live button, if there is one) rather than tap a button that refuses (#67). `check-help` reads `help('…')` literally where a widget is placed, so a component that takes its anchor gets the spread `{...help('…')}` from its caller (`AssignmentCard` in UserExercises.tsx). driver.js scrolls only the window to a step's widget; before each step `help/reveal.ts` scrolls the lists it sits in (overflow auto or scroll) just enough to show it, never the page (#67: «Κι άλλο πρόβλημα» under three extra cards on her own screen at 1280×800). Bumping the screen's tour edition instead would re-offer it to kids who played it, when the widget isn't there, and the new bubble would be skipped.
- Sound (`src/sound/`): the kids' screens use a palette of named sounds (`sounds.json`, WAVs in `public/sfx/`, chosen from CC0 Kenney packs by `tools/sfx/`; see its README), played through Web Audio. `SoundProvider` makes every button tap by itself; an element names another sound with `{...sound('open')}` (or `sound('none')` when its handler plays its own), and outcomes are played where they happen (`sfx('correct')`, `sfx('stars')`). `npm run check-sound` (in lint) fails when something she can touch or drag makes no sound. When you add a widget, give it the sound it means.
- Answer fields (#52): in the problem player's calc line (`x op y = result`) and numbers step every box is a button; she taps one and fills it. The selected box has the one focus look, a cyan ring with glow and lift (`answerBox.ts`; cyan means nothing else on these steps, gold is the operation and «what we seek», and the browser's focus ring is off on the boxes, keys and chips). Where each input goes is pure logic in `answerFields.ts` (tested in `answerFields.test.ts`), and each input returns its sound, since check-sound can't see handler branches. Calc: a chip goes into the selected x or y, else the first empty of the two; an operator always into op; a digit into the result, from op or the result. After a fill the focus moves to the first empty box (x, op, y, result; the result when none is), back to x when a line is found, its right sum means nothing in the story or its smaller number comes first (`order`: she swaps the numbers next), and to the result when the sum is wrong («Ξαναμέτρα»), the note `readLine` gave telling which. Numbers: focus moves only with ↵ or a tap. ⌫ erases in the box (calc: on an empty box it steps back to the last filled one before it, never past the start of the line: nothing filled before it is a «nope»); C empties the selected box. An input with nowhere to go wiggles the box and plays «nope», never silence. A tour whose bubbles change gets a new edition in its id (`problem-calc-2`), so the owl offers it again.
